# 段階8（セキュリティ）の方針（案）

2026-10-31 作成。ユーザーの承認を得てから着手する。終わりの条件（roadmap）：カタログ14章のチェックリストが埋まる。

## 前提として分かったこと

- 個人番号：本番では今どこにも保存されていない。読み書きの関数（`employeeSecretsGet`・`employeeSecretsUpdate`）は平文のままで未公開。従業員の画面の「マイナンバー」欄は保存しても捨てられている。
- ログインはメールとパスワードだけ。ロック・セッションの時間切れはない。
- 監査ログは更新の操作だけ（ログイン・PDF出力・検索・CSVは残していない）。
- **Authentication は task-app と共通**（kensyu10171）。ログイン方法の設定や、ログインの前後に動く関数（ブロッキング関数）は task-app のログインにも効く。

## 決めてほしいこと（案と理由）

| # | 項目 | 案（おすすめ） | ほかの案 |
|---|---|---|---|
| 1 | 個人番号の暗号化の鍵 | **Cloud KMS**（同じ Google Cloud のプロジェクトだが Firebase の外の鍵の管理サービス）。関数だけが鍵を使え、Firestore には暗号文だけを置く。費用は月数十円程度 | Secret Manager に鍵を置き、関数の中で AES で暗号化（鍵の取り出しが要る分、漏れたときの影響が大きい） |
| 2 | 個人番号を見るとき | 理由を選んでから（届出の作成・本人からの問い合わせなど）、12桁を1回だけ表示し、専用の閲覧ログ（誰が・いつ・誰の・理由）を残す。ふだんは「●●●● ●●●● 1234」 | — |
| 3 | Googleログイン | Authentication で Google を有効にし（task-app のログイン画面には出さないので影響はない）、ログイン後に**サーバーで会社の許可ドメインかを確かめ**、違えば利用者として扱わない | 許可ドメインをブロッキング関数で判定（task-app のログインにも効くので避けたい） |
| 4 | 5回失敗でロック | ログインの前に関数で「この利用者がロック中か」を確かめ、失敗をサーバーに記録する（5回で30分ロック、管理者が解除できる）。ブロッキング関数は使わない | Firebase の標準の仕組み（大量の失敗の一時的な制限）だけに任せる |
| 5 | セッション | 画面で無操作30分・ログインから8時間で自動ログアウト。サーバーはトークンの発行時刻を見て8時間を超えたら拒む | — |
| 6 | 監査ログの拡充 | ログイン（成功・失敗・IP）・PDF出力・個人番号の閲覧・CSV出力・検索を追加。前の記録の指紋を持たせて改ざんを見つけられるようにする。5年の保存は消さないことで満たす | — |

## 進め方（案）

1. 個人番号（#1・#2）：KMS の鍵を作る（要デプロイ・設定。事前に確認）→ 関数を暗号化に直して公開 → 従業員の画面に表示・入力・閲覧理由 → 閲覧ログ。
2. ログイン（#3〜#5）：ロックとセッション → Googleログインと許可ドメイン（Authentication の設定変更は事前に確認）。
3. 監査ログ（#6）と、認証の変更を全関数に反映する再デプロイ（未公開の7個は除く）。
4. 14章のチェックリストを埋める。全ロールでの一周は段階10。

## 本番への影響と確認すること

- KMS の API を有効にし、鍵を作る（Google Cloud の設定の変更）。
- Authentication で Google を有効にする（task-app と共通の設定）。
- 関数のデプロイ（新しい関数と、認証を直した全関数の再デプロイ）。
- いずれも実行の前にユーザーに確認する。
