# カタログ準拠までの実装手順（統合版）

作成：2026-10-29。`catalog-gap-analysis.md`（中身の正しさ）と `ux-one-way-plan.md`（画面の一本道化・大人数対応）を1本の手順にまとめたもの。以後はこのファイルを正とする。

## 基本ルール

1. **縦に1本ずつ仕上げる。** 1つの業務について「データ項目 → 計算 → 画面（ウィザード）→ 一括操作 → 実ブラウザー確認」までを終えてから次へ進む。
2. **完了の判定はカタログで行う。** カタログの各【項目】をチェックリスト（`catalog-checklist.md`）にし、実ブラウザーで動作を確認できたものだけを完了にする。ビルドやテストの成功だけでは完了にしない。
3. **法令の計算はサーバーの純粋関数に集約する。** 画面側では計算しない。
4. 進行中の「画面再設計v2」の残作業は、このロードマップに吸収する（単独では進めない）。

## 手順

| 段階 | 内容 | 目安 | 終わりの条件 |
|---|---|---|---|
| 0. 保全 | 未コミットの実装をコミット。gitの管理範囲を `shaho-app` に限定。カタログのチェックリストを作成 | 0.5〜1日 | 作業がすべて履歴に残り、チェックリストに現状が記入されている |
| 1. 正しさの土台 | 🔴の計算誤り（端数処理、支払基礎日数、算定の画面計算、免除判定、資格取得月・喪失月、同月得喪）を修正。ウィザードの入力に必要なデータ項目（雇用区分6種、給与形態、適用区分と適用理由、資格取得日・喪失日、住所の分割、現物給与など）を追加 | 4〜6日 | 境界値テストが通り、既存データの移行が済んでいる |
| 2. 共通UI部品 | ウィザード枠（進捗・ステップ一覧・説明・戻る／次へ）、一括型の「対象者一覧」、状態色4種、用語集、デザイントークン | 2〜3日 | 部品だけで画面見本が組める |
| 3. 入社（個人型の見本） | 招待 → 本人入力 → 担当者確認 → 台帳 → 雇用条件 → 承認依頼 → 加入判定・等級 → 資格取得届 → 提出。新卒一斉入社の一括開始も含める | 3〜4日 | 初心者がホームから説明なしで完了できる |
| 4. 毎月の処理（一括型の見本） | 給与取込 → 確認依頼 → 計算 → 確認依頼 → 公開 → 徴収記録。保留・失敗者だけの再実行・バックグラウンド処理を含める | 3〜4日 | 数百名のデータで最後まで通る |
| 5. ホームとナビ | やることリスト（期限順・続きから）、ライフイベントのカード、サイドバーを5項目に整理 | 2日 | どの業務にもホームから迷わず入れる |
| 6. 残りの業務を型に当てはめる | 退職 → 扶養 → 産休・育休 → 算定基礎届 → 賞与 → 随時改定・終了時改定 → 年齢到達 | 各2〜3日 | 業務ごとにチェックリストが埋まる |
| 7. 届出・承認の横断機能 | 不足している届出種別、承認取消・送信取消、模擬申請の段階遷移と受付番号、訂正届・取消届、添付、期限計算、一括承認、差分表示、ZIP | 4〜5日 | 12種すべてが作成から提出記録まで通る |
| 8. セキュリティ | 個人番号の暗号化・閲覧理由・閲覧ログ、Googleログイン、ログインロック、監査ログの拡充 | 2〜3日 | 14章のチェックリストが埋まる |
| 9. 周辺機能 | ポータルからの申請、ダッシュボードの集計とカレンダー、帳票、シミュレーション5種、料率CSV取込と額表の閲覧 | 5〜7日 | 11〜13章のチェックリストが埋まる |
| 10. 総合確認 | 千人規模のテストデータ、全ロールでの一周、旧画面の撤去 | 2〜3日 | チェックリストがすべて埋まる |

合計の目安は約40〜50日。業務の順番（段階6）は、実務で多い順に入れ替えてもよい。

## 段階1を先に行う理由

- 画面を一本道にしても、計算結果が間違っていれば実務で使えない。
- ウィザードの入力項目（雇用区分・給与形態など）が足りないまま画面を作ると、項目を追加するたびに画面を作り直すことになる。

## 着手前に決めること

1. 画面再設計v2の残作業を止めて、このロードマップに吸収してよいか。
2. 届出の状態管理：内部は3軸（社内承認・模擬申請・紙提出）のまま維持し、画面ではカタログの状態名（下書き〜完了）で表示する方式でよいか。
3. gitの整理：`shaho-app` を独立したリポジトリにするか。
