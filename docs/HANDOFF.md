## 3. 決定事項（ユーザー承認済み）

- **縦に1本ずつ仕上げる。** 1業務ごとに「データ → 計算 → 画面 → 一括操作 → 実ブラウザー確認」を終えてから次へ進む。
- **完了の判定はチェックリストで行う。** 実ブラウザーで確認できた項目だけを ✅ にする。ビルドやテストの成功だけでは完了としない。
- **法令計算はすべて `functions/src/insurance/calculator/` に置く。** 画面では計算しない。画面から送られた値を信用せず、サーバーで再計算して承認申請する。
- **手続きは2つの型にする。** 個人型（1人分のウィザード）と一括型（対象者一覧。要対応の人だけを表示し、全員に一括操作、例外の人は保留にして個別対応、失敗した人だけ再実行）。見本は、入社＝個人型、毎月の処理＝一括型。
- **届出の状態**：内部は3軸（社内承認・模擬申請・紙提出）を維持し、画面ではカタログの状態名（下書き〜完了）で表示する。
- 画面再設計v2の残作業は単独では進めず、ロードマップに吸収する。
- サイドバーは5項目（ホーム／手続きを始める／毎月の処理／従業員／承認＋その他）に整理する予定。

## 6. 作業上の注意

- **デプロイ**：Bash からは firebase CLI が起動できないため、PowerShell から実行する。関数名を明示した限定デプロイにする：
  `firebase deploy --only functions:default:<名前>,functions:default:<名前> --project kensyu10171 --non-interactive`
  コードにあっても未公開の関数が13個ある（`employeeSecretsGet` など。個人番号が平文のまま）ため、全体デプロイはしない。別アプリの codebase `socialinsurance` にも触れない。
- **Firestore の索引**：`firestore.indexes.json` は本番（79件）より古い（63件）。索引をデプロイする場合は、本番の定義（`firebase firestore:indexes`）と合わせたものを使う。本番の索引を消さないこと。索引のデプロイには明示の承認が必要。
- **本番への書き込み・デプロイ・Hostingの公開は、事前にユーザーに確認する。** 本番の認証にパスワードを入力しない（ログインはユーザーが行う）。
- 開発サーバー：`.claude/launch.json` の `angular-dev`（ポート4201。本番のFirebaseに接続）。Callable の通信はブラウザーペインのネットワーク記録に出ない。
- ビルドとテスト：`functions` で `npx tsc --noEmit -p .` と `npx jest --config jest.config.js`、`src` で `npx ng build --configuration development`（以前からの警告 NG8011 が3件出る）。
