## 1. 料率改定時の切替処理（6章）

**今の状態**
- 料率の CSV 取込（`functions/src/insurance-rates/service.ts`）は、同じ区分の前の料率に終わりの月を付けてから新しい料率を足す。料率は月単位で持ち、計算は対象月に当てはまる1件だけを選ぶ（`utils/insurance-rate.ts` の `findApplicableRate`）ので、**同じ月に旧料率と新料率が混ざることは今の作りでも起きない**（カタログの「混在しないことを保証」は満たしている）。
- 計算済みの月への影響：
  - 未確定（依頼前）の月：計算時の料率の指紋 `rateFingerprint` と今の料率を比べ、「計算した後に料率が変わりました。計算し直してください」を出す（`monthly/service.ts`）。
  - 依頼中・確定済みの月：何も出ない。料率が変わったことに気づけない。
  - 賞与の保険料：指紋を持っていないので、未確定でも気づけない。
- 取り込みの確認画面は「今の料率との差」だけを出す。新料率での試算（料率改定シミュレーション）は別のタブにある。

**案（おすすめ）**
1. 取り込みの確認画面に「切替月以降で、すでに計算した保険料」を事業所×月ごとに出す（未確定○人・依頼中○人・確定済み○人。毎月と賞与）。料率改定シミュレーションへのリンクも置く。
2. 取り込んだあと：
   - 未確定の月は今の「計算し直しが必要」の表示のまま（自動では計算し直さない）。
   - 依頼中・確定済みの月は、毎月の処理の画面に「確定した後に料率が変わりました。訂正してください」を出し、今ある訂正（`correctPremium`）→計算し直し→承認の流れに乗せる。
   - 賞与の保険料にも指紋を持たせ、同じ表示を出す。
   - 会社あてのお知らせ「料率を切り替えました。○月分以降の計算済みの保険料を確かめてください」を出す。
3. 取り込みの検査に「同じ区分で期間が重なる料率」の拒否を足す（今は同じ開始月だけ止めている）。

**ほかの案**
- 確定済みの月も自動で計算し直す：承認なしに確定した額が変わるので、別担当者の承認の原則に合わない。採らない。
- 切替月より後に計算済みの月があれば取り込みを止める：3月の改定を4月に取り込むような普通の運用ができなくなる。採らない。

**本番への影響**：関数の更新（料率の確かめ・取り込み、`monthlyRunOverview`、賞与の計算と一覧）。データの書き換えはない。画面の確認は、テスト用の保険者IDで料率を取り込んで行いたい（実施の前に確認する）。

## 2. 保険料の遡及＋修正等級（6章「訂正・遡及」・5章「修正等級」）

カタログの2つ（年金事務所の修正指示で過去の等級を変える／等級の誤りが後から分かったときの遡及訂正）は、「過去の等級を直して、その月以降の保険料をまとめて直す」同じ流れなので、1つの機能にする。

**今の状態**
- 等級は `employees/{e}/grades/{適用月}`。手入力の等級は承認を経て同じ適用月の文書を上書きできる（`grades/manual-grade.ts`）が、計算済みの月への案内がない。
- 随時改定・休業の免除は「改定前の等級で計算した月があります。計算し直してください」の案内を出す（`grade-revision/service.ts` の `recalcMonths`）。
- 毎月の処理の「計算し直しが必要」は料率しか見ず、等級の変化は見ない。
- 訂正（`correctPremium`）は1か月ずつ・毎月の処理の画面から。徴収の記録はそのままで、承認し直した額との差が「一部徴収」「取りすぎ」に出る。

**案（おすすめ）**
- 従業員の画面に「等級を遡って直す」（個人型のウィザード）：
  1. 直す等級と適用月、理由（年金事務所からの修正の指示／誤りの訂正）を入れる → 承認の依頼 → 別の人が承認すると等級が確定する（今の手入力の等級と同じ承認）。
  2. 影響の一覧（自動）：適用月から、次の等級の前の月までのうち、計算済みの月（未確定・確定済み）。関係する届出（その等級の `filingId` の届出、同じ期間の算定基礎届・月額変更届）には「訂正届を作る」へのリンクを出す。
  3. 差額（自動）：月ごとに、正しい等級で計算した額と、承認済みの額・徴収済みの額の差（追加で集める／返す）と合計。
  4. まとめて訂正：影響する月をまとめて訂正→計算し直し→確認の依頼まで進める（月ごとの承認は今のまま。承認の画面ではまとめて承認できる）。
  5. 精算の方法：「次の給与で調整する（○月支給）」「別に精算する」を選んで記録する。実際の控除・入金は今の「徴収の記録」で記録する（差額が一部徴収・取りすぎとして出ている）。
  6. 本人への知らせ（下の3）。訂正の前の内容・理由・精算の記録は、今の `corrections` と監査ログに残る。
- 毎月の処理の「計算し直しが必要」に等級の変化も足す（計算時の等級と今の等級が違えば、未確定は計算し直し、確定済みは訂正の案内）。手入力・遅れて承認された等級でも気づける。

**ほかの案**
- 毎月の処理の画面で月ごとに訂正するだけ（今のまま）：月をまたぐと漏れやすく、差額の合計も出ない。カタログの①〜⑤を満たさない。
- 等級を直したら自動で全部の月を確定し直す：承認を経ないので採らない。

**本番への影響**：新しい関数（遡及の開始・取得・確かめ・更新）、等級の承認・毎月の処理の一覧の更新。確認には過去の月が計算済みの人が要る（サンプル改定テスト事業所の REV-0002 などを使いたい。実施の前に確認する）。

## 3. 等級変更・訂正の本人への通知（5章・6章⑤）

**今の状態**：本人ポータルは等級の履歴から「等級が変わりました」（新旧の等級・適用月・保険料の差）を出す（`portal/details.ts`）。ただし知らせはない。お知らせ（`utils/notify.ts`）は会社全体あてで、本人だけに送れない。訂正した月の明細はポータルが毎回読み直すので、承認し直せば新しい額になるが、訂正したことは出ない。

**案（おすすめ）**：お知らせに「あて先の従業員」を足し、本人ポータルではその人あてだけを出す。等級が確定したとき（入社・定時決定・随時改定・終了時改定・手入力・遡及）と、保険料を訂正して承認し直したときに、本人あてに出す。ポータルの明細の訂正した月に「訂正しました」の印と理由を付ける。公開範囲で等級変更を非公開にしている会社では出さない。

**本番への影響**：お知らせの関数・承認の関数・ポータルの関数の更新。ルールの変更は要らない見込み（お知らせは関数経由で読む）。

## 4. 組合健保の料率・負担割合（1章）

**今の状態**：事業所に「協会けんぽ／組合健保」の区分はなく、自由入力の保険者番号（`insurerId`）だけ。料率マスタは本人料率と会社料率を別に持ち、計算は「本人＝標準報酬×本人料率（端数処理）、会社＝全額−本人」なので、**折半でない割合はマスタに入れれば今でも計算できる**。組合の料率は CSV で保険者番号つきで入れられるが、画面から1件ずつ入れる方法はない。

**案（おすすめ）**：事業所に区分（協会けんぽ／組合健保）を持たせ、組合健保なら保険者番号を必須に。設定→料率に「組合健保の料率を登録」（保険者番号・健康保険料率・介護保険料率・本人と会社の割合・適用開始月）を足し、保存は今の料率マスタ（本人料率・会社料率に分けて）にする。組合健保の事業所で組合の料率が見つからなければ計算を止めて知らせる。計算そのものは変えない。

**ほかの案**：事業所に負担割合の項目を持ち、計算で割り振る（マスタの本人・会社料率と二重になる）。採らない。

**本番への影響**：事業所・料率の関数と設定画面の更新。今ある事業所は「協会けんぽ」として扱う（データの移し替えは不要）。確認にはテスト用の組合健保の事業所が要る（実施の前に確認する）。

## 5. 部署の管理・部署別集計（1章）

**今の状態**：部署は一覧の関数だけ（`companies/{c}/departments`）。登録の画面も関数もない。従業員の `departmentId` は受け付けるが存在を確かめない。従業員の画面に部署の欄の準備だけある。分析の部署別は部署名で集めている（同じ名前は合算）。

**案（おすすめ）**：設定に「部署」（事業所ごとに名前・並び順・使う／使わない）。従業員の画面で所属部署を選べるようにし、保存時に部署があるか確かめる。分析の部署別を部署IDで集め、帳票（従業員別明細・事業所別月次一覧）にも部署で絞り込みを足す。使っていない部署は「使わない」にして消さない。

**本番への影響**：新しい関数（部署の作成・更新）、従業員・分析・帳票の関数の更新。ルールの変更は不要（関数経由）。

## 6. 事業所ライフサイクル（1章）

**今の状態**：事業所は `isActive` だけ（作成時 true、変える手段なし）。配属のとき事業所があるかしか見ない。廃止の操作はない。

**案（おすすめ）**
- 新設：「配属できる」条件＝管轄年金事務所・事業所番号・都道府県が入っていて、料率が見つかること。足りなければ、入社・従業員の登録・異動の行き先で選べない（理由を出す）。事業所一覧に「設定が終わっていません（足りない項目）」を出す。
- 廃止：在籍している従業員が0人（退職済みは除く）で、進行中の手続きがないときだけ「廃止する」（廃止日つき）。廃止した事業所は消さずに残し、選択肢からは外し、過去の保険料・届出からは見られる。監査ログに残す。

**ほかの案**：廃止しても選択肢に残す（誤って配属しやすい）。

**本番への影響**：事業所・従業員の作成・入社・異動の関数の更新。**今の本番の事業所で項目が足りないものがあると、そこへの入社・異動ができなくなる**ので、出す前に本番の事業所の項目を読み取りで調べて報告する（足りない事業所は、サンプル事業所なら止めてよいか確認する）。

## 7. 社会保険労務士情報（1章）

**今の状態**：会社情報の更新の関数は `laborConsultant`（氏名・登録番号）を受け付けて保存するが、取得・画面・届出の PDF・保存原本では扱っていない。

**案（おすすめ）**：会社情報の画面に「社会保険労務士（委託している場合）」の入力欄（氏名・登録番号、任意）。入っていれば、公式様式の社労士の記載欄に記入する。承認時の保存原本にも残し、作り直しても承認時の内容になるようにする。様式ごとに記入位置を合わせるので、まず届出の多い様式（資格取得届・資格喪失届・月額変更届・算定基礎届・賞与支払届・被扶養者異動届）から行い、残りは同じ作りで足す。

**ほかの案**：画面だけ作り、PDF には書かない（カタログの「届出書の社労士欄に記載」に合わない）。

**本番への影響**：会社情報の取得・更新、届出の PDF の記入（画面側）、保存原本の関数の更新。

## 8. 様式のバージョン管理（9章）

**今の状態**：公式様式の PDF をアプリに同梱し、出所・確認日・SHA-256 を `sources.json` とサーバーの `FORM_VERSIONS` に持つ（テストで一致を確認）。承認時の保存原本に様式の版を残し、作り直すときに今の様式と違えば警告を出す。管理者が画面から差し替える機能はない。

**案（おすすめ）：段階10に回す**。様式が変わると記入位置もコードで直す必要があり、PDF だけを画面から差し替えても使えないため、「コードと一緒に差し替える」今の運用が安全。段階10で、古い版の PDF を残して保存原本は承認時の版で作り直す作りと、設定に版の一覧（出所・確認日）を出す画面を足すか決める。

**ほかの案**：管理者が PDF を Cloud Storage に上げて差し替える（記入位置が合わず崩れる恐れ。位置の設定まで画面にすると大きい）。

## 進め方
