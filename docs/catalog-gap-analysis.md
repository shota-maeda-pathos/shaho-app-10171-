# 機能カタログ乖離分析と改修案

作成：2026-10-29。対象はカタログ（第2版）、screen-flow v4、api-design、firestore-schema と、`functions/src`・`src/src/app` の現行ソース（未コミット分を含む）。

重要度の凡例

- 🔴 **法令上誤った結果が出る**（保険料・等級・期限が間違う）。最優先。
- 🟠 **カタログの業務フローが通らない**（途中で手作業や回避策が必要）。
- 🟡 **機能・項目が欠けている**（フローは通るが実務で不便）。
- 🟢 付加的な機能。

---

## 0. 根本原因（なぜ改修がうまく進まないか）

1. **土台のデータモデルがカタログより薄い。** 従業員・雇用・給与のドキュメントに、カタログが前提とする項目（住所の分割、旧姓、外国人情報、被保険者整理番号、資格取得日・喪失日、雇用区分6種、給与形態、契約期間、現物給与、遡及差額など）がない。上位の機能（届出・算定・随時改定・PDF）はこれらを参照するため、上に何を作っても穴埋めの改修が続く。
2. **設計書自体がカタログを網羅していない。** 届出種別はスキーマ設計書で9種類（カタログは12種類＋変更届・訂正届・取消届）。API設計書は従業員と扶養家族しか詳細化していない。届出ステータスの体系もカタログ（直列7段階＋差戻し・返戻・取消）とスキーマ（3軸）で食い違っている。設計書と実装の両方がカタログからずれている。
3. **設計書と実装も食い違っている。** 例：`dateOfBirth`(string) と `birthDate`(Timestamp)、`resignDate` と `resignationDate`、`secrets/{type}` と `secrets/main`、`certificationDate` と `qualificationDate`。どちらが正なのか決まっていない。
4. **業務計算がフロントエンドにある。** 算定基礎届の一覧は画面側に等級表をハードコードし、現行等級を「平均×0.8」で推定し、標準報酬月額に平均額をそのまま保存している（`santei-list.ts:192,235`）。カタログの「サーバーサイドで検証」の原則に反する。
5. **横に広げすぎて縦に完成していない。** Phase 1〜5、カタログ準拠改修、画面再設計v2、サイドバー刷新が並走し、どの業務も最後まで通っていない。`procedures/`・`operations/`・`analytics/` などの大きな実装が**未コミット（untracked）のまま**になっている。

## 改修案

### 方針

1. **新しい画面は作らず、土台→計算→業務の順に縦に仕上げる。** 画面再設計v2の残作業は一時停止する。
2. **法令計算はすべてサーバーの純粋関数に集約し、テストで固める。** 画面には計算させない。
3. **業務ごとに「カタログの文章どおりに一周できる」ことを完了条件にする。** ビルド成功やサービス試験の成功だけで完了としない。

### Step 0：現状の保全（半日）

- `procedures/`・`operations/`・`analytics/` などの未コミット実装をブランチにコミットする。
- このリポジトリのgitルートがデスクトップ全体になっている（`../../shakai-hoken`、`.lnk` まで追跡）。`shaho-app` を独立したリポジトリにするか、`.gitignore` を整備する。

### Step 1：データモデルv2と設計書の更新（2〜3日）

- `firestore-schema.md` を先に更新し、カタログの全項目を持つモデルを確定する（15章の表）。
- `types/firestore.ts` と Zod スキーマを追従させる。既存データは既定値で読み替え（移行スクリプト1本）。
- 届出ステータスは「社内承認（workflow）」「模擬申請（mock：送信済み→受付済み→処理中→完了／返戻）」「紙提出（paper）」の3軸を維持する。そのうえで、カタログの単一ステータスを派生表示する関数を1つ用意する（取消・期限超過はフラグ）。両方の要件を満たせる。

### Step 2：計算エンジンの作り直し（3〜4日）🔴をすべて解消

`functions/src/insurance/calculator/` に純粋関数で集約し、境界値テストを書く。

- 端数処理（50銭ルール、会社負担＝合計−本人負担、労使協定の別ルール）
- 等級の当てはめ（料率マスタの `gradeTable` を使用。画面のハードコードを廃止）
- 支払基礎日数の判定（一般17／パート15特例／短時間11、算定と随時で別ルール）
- 資格取得月・喪失月・月末退職・同月得喪
- 年齢到達（40/65/70/75）
- 産休・育休の免除（月末・14日・賞与の1か月超）
- 資格取得時決定（月給・日給・時給）

### Step 3：業務フローを1本ずつ完成（各2〜4日）

順番は実務の発生頻度と依存関係で決める。

1. **入社**：招待→本人入力（仮データ）→担当者承認→台帳→雇用条件→別担当者承認→適用判定→取得時決定→資格取得届→PDF→模擬申請
2. **月次**：給与→承認→計算（無給休職・適用外・免除を正しく扱う）→確定→公開／徴収
3. **退職**：喪失届・最終月判定・未徴収の個別算出・アカウント3段階
4. **算定基礎届**：サーバー側で対象者抽出と除外理由→判定→一括承認→9月適用→複数人PDF
5. **随時改定・終了時改定**
6. **休業**：産前産後の日数自動計算→申出書→承認で免除反映→変更届・終了届
7. **賞与**：同月合算・上限・不支給報告書
8. **扶養**：収入要件チェック・本人申請

### Step 4：届出・承認・模擬申請の仕上げ（3〜4日）

不足している届出種別、承認取消・送信取消、模擬申請の段階遷移と受付番号の連番、エラーシミュレーション、訂正届・取消届、添付、期限計算、一括承認、差分ハイライト。

### Step 5：セキュリティ（2〜3日）

個人番号の暗号化（鍵は Secret Manager）・閲覧理由・閲覧ログ、Googleログインと許可ドメイン、ログインロック、監査ログの拡充（IP・ログイン・PDF）。

### Step 6：周辺機能

ダッシュボードのカード10種とカレンダー、ポータル申請、帳票とZIP、シミュレーション5種、料率CSV取込と額表閲覧。
