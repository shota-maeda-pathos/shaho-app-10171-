# 画面構成改修v2 実装の引継ぎ

更新：2026-10-29。v2全体の完成宣言ではなく、実装済み範囲と残作業の記録。

## 先行して補った範囲

- `/home`をホームの正規ルートとし、旧`/dashboard`の互換リダイレクトを維持。
- ホームの最上部から進行中案件へ戻れる導線と、手続きを始める入口を追加。従来の壊れた届出詳細リンクを修正。
- `/procedures/new`を追加。業務と対象従業員を選んで、既存の入社・退職・異動・扶養・休業・随時改定・算定・賞与の入力画面へ案内。ここではデータを変更せず、実際の登録操作後の既存案件生成に接続する。
- 従業員詳細のクエリパラメーターで退職・異動パネル／扶養・休業タブを開けるようにした。
- 入社画面の「入社手続きが完了」という早すぎる表示を、登録・届出準備の完了へ修正。承認・提出に進むリンクを追加。
- 案件詳細に、実データを再検証して保存する完了確認API・ボタンを追加。単純なステップ番号加算は行わない。
- 模擬申請または紙提出受理から確認できるように修正。模擬だけの完了は実提出と区別して表示。
- 社内承認前の提出作業はブロック。再承認待ち・参照先削除を判定へ反映。
- 退職案件は精算が残れば全体完了にしない。精算待ちでも他の届出作業は進められる構成を維持。
- 取消・完了済み案件は閲覧時の再計算で履歴を変更しない。
- 関連届出から承認状況を判定し、旧フックで承認参照が欠けた個人案件も表示時に補完する。
- 同じ従業員の別種の案件へ届出を紐付けるフックの誤りを修正。
- 案件の単件取得は権限確認してから関連情報を読み取り・更新。異動先の権限も確認。
- 担当事業所が空の場合の全件取得経路を修正。指定事業所もサーバーで検証し、31以上の担当事業所では個別事業所の選択を求める。
- 案件ID・会社ID・一覧カーソル等にパス区切りを含められないようにした。
- 一覧・詳細の取得失敗を空データとして隠さず再試行を表示。一覧の応答順の逆転と追加読込の二重実行を防止。
- 案件一覧の絞り込み用索引を追加。同一Firebaseプロジェクトの既存42索引・fieldOverridesを保持した配信用定義で反映。

## 検証

- 案件の回帰試験13件成功（完了経路、自己の確認操作の再試行、権限、取消履歴、承認前ブロック、退職の残精算、関連文書の種別）。
- 保険料・ポータル・賞与の既存関連試験95件成功。
- Functions全体のTypeScriptビルドとAngular開発ビルド成功。既存のアイコン投影警告3件が残る。
- 認証済みの実ブラウザーによる業務一周は未確認。ビルドとサービス試験での確認を実操作済みと扱わない。
- 配信確認：索引の反映と、対象16 APIの配信完了を確認。一覧・詳細・更新・取消・完了確認のAPIはサーバーに未作成だったため今回作成。画面はローカルのソースへ反映した。

## 今回追加した範囲（事業所・定例業務・ナビゲーション）

- サイドバーをホーム／手続き／定例業務／従業員台帳／承認／届出・帳票／集計・試算／設定の8項目に整理。ロールに応じて表示する。
- 管理画面の上部に事業所切替を配置。アクセス可能な事業所だけを取得し、選択をURLと利用者別セッションへ保存。切替時は入力消失を確認し、画面を再生成する。
- 従業員・給与・届出・承認・手続き・保険料一覧と集計の取得に事業所指定を接続。APIでも担当外の指定を拒否する。
- `/operations` に事業所×対象月の対象者別状況を追加。不足情報、給与・保険料の承認、公開、保留理由を表示する。人数は読み込み済み対象者の集計と明示し、追加読み込みを用意。
- 保留理由は版番号を確認して保存し、監査記録を残す。保留中の対象者は一括処理しない。
- 選択した対象者の計算・保険料承認申請・明細公開を既存の実処理に接続。1回100名まで、個別の結果と直近5回の履歴を保存する。同一操作IDの再実行を制御する。
- 給与の直接確定を廃し、承認申請に変更。申請中の編集を拒否し、承認対象の会社・従業員・種別をサーバーで照合する。自己承認の既存禁止を維持。
- 明細公開は給与・保険料の両方が承認済みであることを取引内で確認。複数名の公開と再試行を処理し、失敗者を個別表示する。
- ホームの給与・計算の別々の入口を定例業務へまとめ、手続きを始める入口を統一。権限に応じてタスクとショートカットを表示する。
- `/analytics` に確定済み保険料の集計と試算を分離。届出件数は最新10件だけから数える方式を改め、全件の集計へ変更。ホームから重い分析の自動取得を外した。
- 本人ポータルを管理画面とは別レイアウトにし、従業員のみの利用者をポータルへ案内。退職後の利用期限をAPIでも検証する（明示期限、なければ退職日から3か月）。共用の認証アカウントは停止しない。
- 徴収画面の「承認済みなら徴収済み金額を自動設定」を撤去。徴収済み額の合計を理由付きで記録し、版番号・監査ログを保存。未記録、一部徴収、過徴収を区別する。ホームの未徴収警告も本人負担と実際の徴収額との差で判定する。
- 画像の手続き一覧の INTERNAL は索引構築中の FAILED_PRECONDITION と確認。構築中の日本語案内と再試行を表示する。

## 続けて実装する範囲

1. 入社前の招待・本人入力・担当者承認・正式登録の区別。登録だけで全業務完了と表示しない。
2. 休業・扶養・異動・算定・賞与の全作業の実データ判定。batchの全参照・対象者別結果の集約を補う。
3. 自動案件生成の一意キー、業務更新後に同期だけ失敗した場合の再試行、既存未完了届出・承認の紐付け移行。
4. 案件のメモ・担当・優先度編集UI、関連文書、通知・期限の統合。
5. 月次処理の中断からの画面上の再開、古い実行履歴のページング、大人数の進捗表示と処理上限の改善。APIの同一操作ID制御だけで全操作の完全な復旧を保証したとは扱わない。
6. 認証済みの複数ロールで、事業所切替→入力→別担当承認→公開→本人閲覧の一周確認。
7. 全ての旧画面・CSV操作で事業所表示と更新範囲が一致するかの確認。今回の主要一覧・集計の適用だけで全経路の統一済みとしない。

## 実務品質へ向けた既存実装の課題

- 算定基礎届の旧一覧は平均額から現在等級を仮定する推定処理が残り、支払基礎日数等の取得・正式な等級判定も十分でない。この結果を実務の正式決定として扱わず、承認経路を含めて優先的に作り直す必要がある。
- 旧給与一覧の既定20名、旧算定一覧の100名など、既存画面のページングを補う必要がある。新しい定例業務の対象者一覧には追加読み込みがある。
- 資格取得・喪失月、月末在籍、免除・年齢境界等の法定条件は計算処理全体の追加検証が必要。新しい対象者一覧の在籍期間判定だけで法定計算が完成したとはしない。
- 旧データの支援金が未計算なら再計算・再承認が必要。既存の承認済み金額を自動で書き換えない。
- 徴収額は担当者が記録した実績であり、銀行連携や給与ソフトの実控除結果との自動照合ではない。
- 退職案件の精算データ作成済みと回収完了の区別も継続確認する。
- 手続き開始は既存入力への案内を含み、全種別の新ウィザードは未完成。市販製品と同等の完成・実務検証済みとは宣言しない。
